# 一个任务，怎样做到更快、更便宜、更可靠

[返回首页](../README.md)

这是一份建议流程，尚非本项目实测得出的最优方案。先解决真实失败，再增加系统复杂度。

## 1. 选任务，先写验收

选一个范围明确、能重复运行、能判断结果的场景。不要用「做一个全能助理」作为第一次实验。

写清楚输入、输出、权限、预算和停止条件。把验收项拆成硬约束与质量标准。硬约束失败就判失败，例如数字不一致、漏掉破坏性变更、未经授权发布。

使用 [任务契约](../templates/task-contract.md)。验收标准应在运行前固定，避免看见输出后临时降低要求。

## 2. 建立简单基线

先考虑脚本、固定工作流或单 Agent。如果确定性工具就能解决，不必专门增加一次模型调用。

冻结一组输入及其版本，保留一部分任务作为未用于调试的验证集。记录模型标识、参数、工具、指令和环境版本。无法冻结的外部来源要记录抓取时间及变化限制。

一轮演示只能说明系统在那一次运行中发生了什么。需要重复试验，才能观察稳定性。

## 3. 给上下文分工

| 信息 | 建议放置方式 | 维护要点 |
| --- | --- | --- |
| 当前目标与硬约束 | 当前上下文 | 变更时明确覆盖旧要求 |
| 完整材料与操作证据 | 外部文件或存储 | 可定位、有版本、来源可查 |
| 当前进展与阻塞 | 结构化状态记录 | 在重要状态变化后更新 |
| 长期偏好与经验 | 可维护记忆 | 标记适用范围、复核时间和失效条件 |
| 技能说明 | 按任务需要加载 | 入口简明，细节按需读取 |

不要只追求摘要短。摘要必须保留影响决策的约束、证据位置和未解决问题。对 compact 与 reset 使用相同任务比较恢复质量，参考 [交接模板](../templates/context-handoff.md)。

## 4. 工具要能执行，规则要能落地

工具接口应说明输入、返回值、错误与副作用。区分只读、修改和发布权限。对产生外部影响的动作，记录是否执行成功，避免把网络超时误认为动作没有发生。

为预算、重试和恢复设置可执行的限制。反复重试同一失败通常需要诊断，而非继续烧 token。达到预算或无法判定外部操作状态时，应按任务契约停止并交接。

这些机制属于实现要求；复制本仓库的 Markdown 不会自动给某个 Agent 安装权限或预算控制。

## 5. 只有收益明确时才拆分角色

适合拆分：相互独立的资料查找、可隔离的代码模块、需要单独标准的验收。

不适合直接并行：紧密依赖同一可变状态、频繁互相确认、共享文件容易冲突的步骤。先定义输入输出与责任，再讨论角色名称。

审查者先拿标准和原始证据，再看解释。即便角色分开，也要防止共同盲点。使用 [验收清单](../templates/acceptance-review.md) 记录漏检和误报。

## 6. 记录全程，而不只截取成功那次

每个任务保留：任务 ID、开始结束时间、配置版本、工具调用与返回状态、产物、验收结果、成本与人工介入。敏感内容在公开前脱敏。

报告至少包含：

- 通过数 / 总任务数，以及失败原因分布。
- 端到端耗时；样本足够时给中位数与尾部耗时，注明样本量。
- 全部尝试成本与每次合格交付成本；标明币种和计费口径。
- 人工检查与返工时间；说明是否折算进成本。
- 权限越界、重复操作、恢复失败等严重事件的实际次数。

缓存命中、并发程度、工具延迟和人工等待会影响结果，应一并记录。速度与准确性可能需要取舍，先定义不可牺牲的质量门槛。

## 7. 一次只改一个因素

| 观察到的问题 | 可测试的改动 | 需要观察的副作用 |
| --- | --- | --- |
| 无关历史干扰 | 按需检索或显式交接 | 必要证据是否丢失 |
| 漏掉固定要求 | 添加可执行验证 | 检查是否只验证了格式 |
| 工具选错 | 精简接口与说明 | 必要能力是否也被移除 |
| 总成本高 | 确定性步骤改脚本或调整模型路由 | 重试与返工是否上升 |
| 长任务失去状态 | 增加检查点与恢复校验 | 状态是否过时、外部操作是否重复 |

先冻结任务集、预算和验收，改变一个因素，然后复跑。下一轮用保留任务检查，防止只对调试样例有效。实验结果用 [实验报告](../templates/experiment-report.md) 公开，包括负面结果。

## 8. 维护可以删减的系统

模型和工具会变化，过去必要的提示、路由或角色后来可能成为负担。定期做消融：删掉一个组件，看质量与成本是否真的变差。

一次失败不一定意味着需要再加一个 Agent；也可能意味着输入错误、工具不稳定、验收模糊，或者这个任务根本不需要自主决策。
