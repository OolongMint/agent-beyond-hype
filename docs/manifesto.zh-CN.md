# 从拟人理解 Agent，到超越拟人设计 Agent

[返回首页](../README.md) · [English overview](../README.en.md)

> 以下是我的观察、主张与待验证的设想。引用用于支持具体技术背景，不能替个人判断背书。

## 1. 我最初如何理解 Agent

我习惯把 Agent 想成一个人。

传感器像五官，接收外界信息。对自动驾驶系统来说，外界是变化的道路与交通；对交易系统来说，外界是变化的市场。到了软件 Agent，文件、网页、数据库和 API 返回的信息，都可以成为感知输入。

执行器像四肢，使系统能够改变环境：修改文件、运行程序、提交请求、操作设备。模型则像参与理解和决策的大脑。

这个比喻好懂，但它只是比喻。API 既可以读取信息，也可以执行操作；LLM 不是人脑的复制品；自主性也不是某个模型组件，而是整个系统在目标、权限和反馈约束下自行推进任务的程度。

对我真正有用的结构是：**观察环境 → 形成当前状态 → 选择行动 → 执行 → 检查结果 → 调整下一步。**

Anthropic 在 [Building effective agents](https://www.anthropic.com/research/building-effective-agents) 中区分了预设控制路径的 workflow 与由模型动态决定过程的 agent。这个区分提醒我：自动运行与自主决策不能简单画等号。

## 2. 我期待的终点，是从表达意图到可靠交付

我理想中的体验很朴素：我说出想法，AI 理解要求、补齐必要信息、完成执行，最后交付合格结果。

「全部完美完成」是一种愿景，目前不能当作普遍成立的产品能力。想法本身可能含糊，目标之间可能冲突，外部环境也会变化。系统越自主，越需要明确何时继续、何时停止、何时请人判断。

AGI 是讨论更广泛能力的一个方向，但不是每个 Agent 项目的必要目标。把一个限定场景做好，也有独立价值。

我原本把「模型知道得比人多」理解成「因此会超越人类」。更准确地说，训练数据规模不能直接推出可靠性、通用推理或现实行动能力。知识覆盖、解决问题、长期规划与兑现结果，是需要分别考察的维度。

## 3. 昂贵专家的比喻：好用，但仍然不完整

使用 Claude Code、Codex 一类工具时，我有时觉得自己雇了一位知识广、反应快、按使用量计费的专家。简单操作也交给它，总有一种「让专家帮我拧瓶盖」的感觉。😭

但模型不会什么都知道，昂贵也不保证适合每个任务。它能否主动推进，还取决于产品设计、授权范围、工具和反馈机制，不能一概描述成「有问必答的百科全书」。

所以我会重新判断工作分配：稳定的计算交给程序，重复流程交给脚本，需要理解和判断的环节再交给模型。判断依据是质量、速度和总成本，而非每一步都要显得智能。

## 4. 我对概念热潮的怀疑

当我看到 personal agent、memory、skills、harness 等词不断出现时，第一反应是：这里面有多少是真正的新东西？

许多使用者早就在组合指令文件、工具、记忆、任务拆分和调度。把这些能力打包、迁移到云端、连接个人工作场景，可能改善体验，但不能仅凭命名就认定发生了底层突破。

**我的怀疑是：一部分行业叙事可能把工程整合描述成智能跃迁。** 这是对传播方式的判断，不能据此断言某家公司为了融资而故意炒作，也不能从组件相似直接推导产品没有价值。

反方有一个很强的理由：可靠的集成本身就很难。权限、连接稳定性、恢复能力、可观测性与持续维护，都可能决定用户能不能真正用起来。新的组合未必是新原理，却可能创造新的可用性。

因此，我想用四个问题审视一个新概念：

1. 它具体改变了系统中的哪个机制？
2. 在相同任务上，相比简单基线改善了什么？
3. 改善的代价与失败条件是什么？
4. 去掉这个组件，结果会不会变差？

怀疑应当推动测量，而不是提前替测量写好结论。

## 5. 从 PE 到 harness：相连，但不相等

我的直觉是：很多效率问题，最终仍与「把需求讲清楚」有关。这个直觉有价值，但不够覆盖整个系统。

| 层次 | 我关心的问题 | 例子 |
| --- | --- | --- |
| Prompt Engineering | 本次应该怎样理解与输出？ | 目标、格式、边界、示例 |
| Context Engineering | 此刻应该看到什么信息？ | 检索、时效、压缩、状态摘要 |
| Harness Engineering | 整个任务如何运行并交付？ | 工具调用、预算、重试、权限、验证、恢复 |

这个分层是本文的工作定义，实际产品的边界可能重叠。个性化 Agent 是针对个人场景的应用；harness 是支撑运行的系统，两者不属于同一个分类轴。

一句「失败后不要重复发布」是提示词。真正阻止重复发布，还需要状态记录、幂等机制或发布状态检查。一句「控制预算」也不能替代可执行的计量和停止逻辑。

因此，好的 harness 包含好的提示词，但不能只靠提示词完成。

## 6. 上下文不是越多越好，也不是越少越好

我不喜欢把所有文档、历史和技能一股脑塞给模型。尤其是过期说明，可能和当前任务互相冲突。

这不意味着长上下文本身有错。复杂任务可能确实需要大量材料。真正的问题是：材料是否相关、准确、及时，而且在需要的时候能被找到。

Anthropic 的 [上下文工程文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) 讨论了信息筛选，并把压缩、结构化笔记和多智能体作为长任务的不同手段。因此，「官方建议上下文满了就 reset，不要 compact」不是准确概括。

我的实践提案是：把完整证据放在外部，把当前目标和必要状态放在工作上下文中。给重要记录标记来源、时间、适用范围与失效条件。在切换任务或恢复会话时，检查旧结论是否仍然成立。

compact 适合延续工作但减少历史体积；reset 加显式交接适合需要重新建立工作上下文的情况。两者都可能丢信息，都需要恢复验证。不能用一个固定阈值替代对任务状态的判断。

## 7. 做事的人和验收的人，可以分开；标准必须先有

模型说「我做完了」，不能成为完成的唯一证据。写得自信也不是正确性指标。

我倾向于把执行与验收职责分开：执行方产生产物和证据，验收方对照预先定义的标准检查。有明确答案的地方，优先用测试、计算、规则或源数据核验。

独立 reviewer 可以是人、检查程序或另一个模型。但拆成两个 Agent，不会自动产生统计独立性；同一个模型家族也可能共享盲点。审查者如果只看执行者的总结，就仍可能被错误叙述带偏。

多智能体值得尝试的条件是：任务可以并行、需要隔离上下文，或独立检查确实带来收益。代价则包括通信、重复读取、冲突与额外推理。是否划算，要与单 Agent 的基线比较。

## 8. 快、便宜、准确：把目标变成能比较的东西

我最关心的问题始终是：如何以更少成本，更快交付合格结果？

这里的「准确」需要转化成具体要求。发布说明里的事实准确、程序通过测试、研究材料来源可追溯，是不同的验收方式。统一口号不能替代任务定义。

我建议记录五项：通过率、端到端耗时、全部尝试成本、人工介入时间和失败类型。总成本应包括失败重试，而不只是最终成功那次的 token。

OpenAI 的 [Agent improvement loop](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop) 展示了将运行记录、人工与模型反馈转成评估，再据此修改系统的过程。对我而言，值得借鉴的是把失败变成下一次可以检查的要求。

一次只改一个因素，用事先留出的任务验证。调试集上表现更好，不等于实际场景已经更好。模板中的轮数和预算只是试验起点，不是普遍最优值。

## 9. 拟人帮助我们理解，也可能限制我们设计

我的进一步疑问是：我们为什么这么习惯让 AI 像人一样工作？

多智能体被解释成团队，记忆被解释成人的经历，规划被解释成深思熟虑。这些类比降低了理解门槛，但类比不是技术起源证明。反应式与规划式设计也不能只归因于模仿人的直觉和思考，它们还来自控制、搜索和优化等技术传统。

研究人的认知、行为和组织方式，可以带来启发。但如果把人类工作流程当成必须复制的蓝图，我们可能会复制本来不必存在的沟通与协调成本。

机器可以更自然地使用结构化中间状态、直接调用 API、批量搜索候选方案、并行运行检查，或把确定性问题交给计算器和求解器。它不必先开一个虚拟会议，才能改变一个配置。

这些方式也并不意味着「不受人类价值和权限约束」。我想突破的是执行路径上的拟人习惯，目标与责任仍需由人定义。

## 10. 把「突破人的框架」变成可检验的问题

「让 AI 不按人的逻辑思考」太抽象，也很难从外部直接验证内部推理机制。更可行的起点是比较可观察的系统设计。

| 待检验假设 | 对照方法 | 可能推翻它的结果 |
| --- | --- | --- |
| 结构化状态优于长篇交接 | 相同任务下比较 JSON 状态与自然语言摘要 | 字段丢失隐含约束，失败更多 |
| 直接 API 比界面模拟更有效 | 相同权限与目标下比较调用路径 | API 覆盖不足、维护成本更高 |
| 批量搜索比串行讨论更适合部分任务 | 固定总预算比较候选生成与筛选 | 候选重复、筛选错误、总成本上升 |
| 可执行检查比角色数量更影响质量 | 固定模型，分别增加检查与增加角色 | 检查覆盖不足，而分工显著提升结果 |

这些是我的研究设想，尚未在本项目中得到实测支持。它们不会证明某种架构实现了 AGI，但可以帮助我们更具体地回答：哪些人类工作习惯值得保留，哪些可以舍弃？

我希望这个项目最终积累的，是能被推翻的主张、可复现的实验和可以直接拿去用的任务方法。

**少一点概念崇拜，多一点交付证据。**
