# 填写样例：把 Git 变更整理成发布说明

[返回首页](../README.md) · [任务模板](../templates/task-contract.md)

> 这是虚构的教学场景与实验计划，没有运行 Agent，也没有实测结果。
> This is a fictional worked brief and evaluation plan, not an executed benchmark.

## 任务契约 / Task contract

**目标 / Goal**：根据冻结的发布材料生成 `release-notes.md`，包含新增功能、修复、破坏性变更、迁移步骤与已知问题。读者是产品使用者。

**输入 / Inputs**：固定的 base/head commit、区间内 PR 的标题与正文快照、变更文件、项目提供的迁移说明。优先使用经过维护者确认的迁移说明；来源冲突时标注冲突，不自行补全事实。

**范围 / Scope**：生成发布说明草稿；不修改代码、不推送分支、不发布 GitHub Release，也不从提交消息推断没有证据的用户价值。

**权限 / Authority**：只读提供的快照，只能写入指定输出目录。网络访问关闭；输入不足时列出缺失项。

**预算 / Budget**：演示用上限为模型与工具调用合计 1 USD、端到端 10 分钟、最多修订 1 次。数字是本例的预设，不是推荐行业标准。运行器需负责计量、超时和停止；人工审查时间另外记录。

**状态 / State**：保存输入版本、已检查条目、草稿与验收记录。恢复后先确认版本、已用预算和现存产物。本任务无外部发布副作用。

## 先固定验收 / Acceptance first

| 项目 / Criterion | 方法 / Method | 判定 / Gate |
| --- | --- | --- |
| 每条发布信息有 PR 或文件证据 | 人工或独立检查逐条核对来源 | 必须通过 |
| 标准答案中的破坏性变更全部出现 | 对照维护者预先标注的集合 | 必须通过 |
| 没有编造功能、兼容性与迁移步骤 | 对照输入逐条核验 | 必须通过 |
| 来源不足的地方明确标注 | 检查有意缺失的样例 | 必须通过 |
| 输出包含要求的五个部分 | 确定性检查标题 | 必须通过 |
| 措辞对使用者清楚、简洁 | 使用固定说明的人工量表 | 单列质量评价 |

标题检查只能证明格式完整，不能证明事实正确。维护者的参考集合也需要检查，不能未经复核直接当作绝对真值。

## 最简单方案 / Baseline

一名 Agent 读取材料，生成草稿；确定性检查负责文件和标题，独立验收负责事实与完整性。保存初稿和最终稿，记录修订成本。

## 只改一个因素 / One change

A 使用上述基线。B 在草稿后增加一个独立模型 reviewer，其输入包含相同材料和相同验收标准。两组保留相同的最终独立验收方式、预算上限和修订上限；B 的额外审查消耗计入预算。

可以预先选取 12 组冻结材料作为小规模试点：8 组用于调试，4 组保留验证，每组重复 3 次并随机交错 A/B 顺序。小规模结果只用于发现问题，不用于宣称通用优势。规模和轮数应依据实际任务与资源调整。

## 专门加入容易失败的输入 / Failure cases

1. PR 标题写「小修复」，正文却包含 API 删除。
2. 两条材料对默认配置的描述互相冲突。
3. 有功能变更，但没有迁移步骤。
4. 多个 PR 重复描述同一用户可见变化。
5. 材料写着计划支持，但当前代码尚未包含。

## 记录结果 / Record outcomes

使用 [实验报告](../templates/experiment-report.md)，比较通过率、总成本、耗时、人工返工、漏检和误报。这里所有结果均为**未测 / unmeasured**。

如果 B 的通过率没有提高，但消耗更多，就不应仅因角色分工看起来完整而保留它。如果 B 提高通过率但明显增加耗时，应报告取舍，由场景决定是否接受。
